# Umbraco.Community.Meganav

Meganav rebuilt for the modern (Lit / web component) backoffice, for Umbraco 14 – 19. A Razor Class Library multi-targeting one .NET version per Umbraco .NET version (see Build). Replaces the legacy AngularJS package in `../Our.Umbraco.Meganav/` (Umbraco 9 – 13).

## Structure

- `Client/` — Vite + TypeScript + Lit frontend.
  - `src/manifests.ts` — single bundle entry, exports a `manifests` array (property editor UIs, modals, property actions + localization). Manifests are left untyped because the `Manifest*` types moved from `extension-registry` (v14/15) to per-package exports (v16+).
  - `src/property-editor/` — the property editor UI element (owns the value, the collapsed state and the looked-up page data; opens the link picker, type picker and item modal) and the `itemTypes` setting's UI.
  - `src/modals/` — `item-type` (edit an item type) and `item` (an item's settings element properties via `umb-property-dataset`/`umb-property`, plus Edit link and Change type). Core modals that moved package after v14 (e.g. the icon picker) are opened by alias with a local `UmbModalToken`, since a missing named import breaks the whole bundle.
  - `src/property-actions/` — Expand all, Collapse all and Populate from tree. Each gets the editor via `UMB_PROPERTY_CONTEXT.getEditor()` and calls a public method on it. They extend `MeganavPropertyActionBase` (built on `UmbActionBase`) because `UmbPropertyActionBase` isn't exported in v14, and their labels are plain text because v14 doesn't localize property action labels.
  - `src/tree/` — a generic sortable, collapsible tree that knows nothing about Meganav (an eslint rule stops it importing from outside the folder). `meganav-tree` is the public element: it takes `items`, a `renderItem` callback for each row and a `canDrop` callback for extra drop rules, owns the collapsed state, and dispatches `MeganavTreeChangeEvent` with the whole value after a drag and `MeganavTreeInsertEvent` from the inline create button. `meganav-tree-level` is one level of it (rendered recursively, one `UmbSorterController` each, plus drag-to-indent/outdent). `tree.ts` has the immutable helpers, generic over `{ id, children }`.
  - `src/components/` — `meganav-item` (one row, rendered by the property editor's `renderItem`), `meganav-preview`, `meganav-actions`.
  - `src/utils/` — shared helpers (`items.ts` Meganav-specific item helpers, `link.ts` item ↔ `UmbLinkPickerLink` mapping and `pickLink`, `entities.ts` page lookups, `item-types.ts` type rules). `entities.ts` calls the Management API `document/urls` / `media/urls` endpoints directly because the generated client's signature changed after v14.
  - `src/types.ts`, `src/events.ts`, `src/lang/` — value types, bubbled events, localization.
  - `public/umbraco-package.json` — the manifest Umbraco discovers at startup. Declares a single `bundle` extension pointing at `/App_Plugins/Meganav/meganav.js`. Umbraco's bundle loader registers any exported array, so `manifests.ts` exports `manifests` and never calls `umbExtensionsRegistry.registerMany()` itself.
- `wwwroot/` — entirely generated by the Client build. Never hand-author anything here.
- C# (namespace `Umbraco.Community.Meganav`):
  - `PropertyEditors/` — `MeganavDataEditor` (alias `Our.Umbraco.Meganav`, the legacy package's, so its data types keep working), its configuration editor (`Models/MeganavConfiguration`), the value editor (`ToEditor`/`FromEditor` re-serialize through `MeganavValueSerializer`, plus references to linked documents and media), `MeganavValueValidator` (max items/depth) and indexing (`MeganavPropertyIndexValueFactory` up to 18, `MeganavPropertyValueHandler` from 19), which indexes item names instead of the raw JSON.
  - `Serialization/MeganavValueSerializer` — the only place the stored JSON is read or written. Reads legacy values too (`title` → `name`, drops the stored URL of linked pages).
  - `ValueConverters/MeganavValueConverter` — `IEnumerable<MeganavItem>` for views and `IEnumerable<MeganavApiItem>` for the Delivery API. Leaves out hidden items, unpublished/trashed/missing pages and items the item type rules no longer allow, and caps the top level at max items. Settings are built with Umbraco's `BlockEditorConverter`, like a block's, so they're the settings element type's model with each value converted by its own property editor.
  - `Models/` — `MeganavValueItem` (stored shape), `MeganavItem`/`MeganavItemType` (published), `DeliveryApi/MeganavApiItem`.
- `../Our.Umbraco.Meganav/` — legacy package. Read it for behaviour (value shape, settings, value converter), not structure.

## Conventions

- Always import backoffice APIs and Lit from `@umbraco-cms/backoffice/*` subpaths, never a bare `lit` import. The backoffice serves these via an import map at runtime; `vite.config.ts` marks `@umbraco` as external so they aren't bundled (duplicates break custom element registration).
- Extend `UmbLitElement` instead of plain `LitElement` where the element needs backoffice context (localization, modals, notifications, etc.) — effectively always.
- Keep `devDependencies.@umbraco-cms/backoffice` pinned to the exact v14 version. Only use APIs that exist from v14 onwards; anything newer must be feature-detected (e.g. `hideTarget` is Umbraco 15+).
- Use Umbraco's built-in UI where it exists: `UMB_LINK_PICKER_MODAL` for link picking, `uui-button-inline-create` for inserting between items, `UmbSorterController` for drag and drop.
- Store the value in the shape documented in `README.md`. It deliberately differs from the legacy package (`name` instead of `title`, plus `id` and `queryString`; `visible` is kept). `MeganavValueSerializer` reads both, and a legacy value is rewritten in the new shape the next time it's saved.
- Settings values are stored as their property editors' editor values and aren't passed through those editors' `FromEditor`/`ToEditor`, so editors that store something different from what they edit (e.g. the media picker's temporary files) aren't supported in settings yet, and their references aren't tracked.

## Build

- `npm run build` (in `Client/`) — type-checks (`tsc`) then bundles `src/manifests.ts` into `../wwwroot/App_Plugins/Meganav/`.
- `npm run watch` — same in `--watch` mode, for live reload.
- `dotnet build`/`publish` on `Umbraco.Community.Meganav.csproj` runs `npm i` and `npm run build` automatically via the `RestoreClient`/`BuildClient` MSBuild targets, which declare Inputs/Outputs so they're skipped when nothing relevant changed. `StaticWebAssetBasePath` is `/`, so the on-disk path under `wwwroot/` is the served path.
- Targets `net8.0` (Umbraco 14), `net9.0` (15 – 16), `net10.0` (17 – 18) and `net11.0` (19), each compiled against the lowest Umbraco version in its range, in one NuGet package. Code that differs uses the SDK's symbols (`#if NET9_0_OR_GREATER` for 15+, `NET11_0_OR_GREATER` for 19+). The target frameworks build one at a time (`BuildInParallel` is off) so the client is only built once.
- One DLL runs on two Umbraco majors for `net9.0` and `net10.0`, so it can only use APIs whose compiled signature is the same in both. Compiling isn't enough: an API that moved to another type (e.g. from `IPublishedContent` to `IPublishedElement`) still compiles but throws `MissingMethodException` on the other major. 18 changed `ApiLink.Content` (added `culture`) and the `Name()` extension, so the `net10.0` build binds those at runtime (`#if NET10_0` in `MeganavValueConverter`), and it reads `ContentType.ItemType` rather than `IPublishedContent.ItemType`, which also moved.
- Known C# breaks to code around: index values (`IPropertyIndexValueFactory` returns `IndexValue` from 15, replaced by `IPropertyValueHandler` in 19), validation (`PropertyValidationContext` from 15), `IPublishedCache.GetById(Udi)`/`GetContentType` (removed in 17; use `GetById(Guid)`), `Name`, `ItemType` and friends (moved to `IPublishedElement` in 18), and `PublishedElement`/`BlockEditorConverter`/`BlockItemData` (changed in 15 and 19).
- The TestSite picks the Umbraco version to run with `UmbracoVersion` (14 – 19, default 17), e.g. `UmbracoVersion=18 dotnet run`, and gets the package's matching target framework.
- Requires Node `^20.19` or `>= 22.12` (per `vite` 7) — check your local Node version before running `npm install`.
